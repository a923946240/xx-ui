## Between servers

Moving to a new server is a database move:

<Steps>

<Step>
### Back up the old server

Copy the database (default `/etc/x-ui/x-ui.db`) and your certificates. See
[Backup & restore](/docs/operations/backup-restore).
</Step>

<Step>
### Install xx-ui on the new server

Use the same install method and a compatible version. See
[Installation](/docs/guide/installation).
</Step>

<Step>
### Restore the database

Stop the panel, put the database in place, restore certificates, and start the
panel. Update any IP/domain-specific settings.
</Step>

</Steps>

## Between xx-ui versions

Within the same backend, upgrading is usually just re-running the installer or
pulling a new image — the panel migrates its own database. Across **major**
versions, read the [release notes](https://github.com/a923946240/xx-ui/releases)
first and take a backup.

## From x-ui

Older x-ui panels can have different schemas. For unsupported sources, set
up xx-ui separately and recreate the inbounds and clients from verified
exports. A successful in-place upgrade of one instance does not establish
database compatibility for other versions or configurations.

### Prepare a 3x-ui migration

The normal installer detects existing installations before changing the
service or database. It continues for a clean host or an identified xx-ui
installation. An existing 3x-ui binary, a recognized panel Docker container,
or an unidentified x-ui service or database stops normal installation.
The migration commands below are explicit and keep the production service
running.

The installer has a separate preparation path for the default systemd and
SQLite installation of 3x-ui v3.10.2 on Linux amd64 or arm64. It supports one
enabled VLESS/REALITY inbound, one bcrypt administrator, and direct or blocked
Xray template outbounds. Instances with custom database paths, traffic quotas,
LDAP, two-factor authentication or additional template listeners require manual review.
It requires Python 3.11 with the tar extraction safety filters, curl, OpenSSL,
and systemd.

```bash
# Read-only compatibility check
bash <(curl -fsSL https://raw.githubusercontent.com/a923946240/xx-ui/main/install.sh) --migrate-3x-ui check

# Backup, isolate, import, and verify
bash <(curl -fsSL https://raw.githubusercontent.com/a923946240/xx-ui/main/install.sh) --migrate-3x-ui prepare
```

Use `backup` to create the backup without downloading or starting xx-ui.
`prepare` verifies the release archive, tests the original client identity and
subscription path on loopback, and writes a candidate database to the private
backup directory printed by the command. It retains known panel and
subscription settings and certificate paths. Historical traffic counters,
existing web sessions, third-party tokens, and other unlisted settings require
separate review. Keep the backup private because it contains the old database
and keys.

Preparation leaves the old service running. Before a separate production
cutover, check for changes since the snapshot, verify certificate renewal and
reverse-proxy configuration, choose a service unit and data directories for
xx-ui, and arrange rollback to the old unit. Verify the old administrator
login, proxy address and HTTPS subscription URL after taking over the ports.

<Callout type="warn">
  Always take a backup before any migration, and keep the old server running
  until you've verified the new one.
</Callout>
